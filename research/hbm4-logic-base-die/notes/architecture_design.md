## Critical Architecture Decisions

### Decision 1: Channel Count Configuration

| Criteria | Evaluation |
|----------|------------|
| Must support | Runtime switch HBM3 (8) ↔ HBM4 (32) |
| Address decoder | Auto recalculate bit fields |
| Bank count | 16/pseudo-ch (HBM3) vs 64/pseudo-ch (HBM4E) |
| Performance | 4× channel parallelism in HBM4 |

**Recommended**: Runtime configurable via HBMConfig with automatic bit field recalculation.

### Decision 2: Pseudo-Channel Demultiplexing

| Criteria | Evaluation |
|----------|------------|
| HBM4 arch | 32 channels × 2 = 64 pseudo-channels |
| Conflict detection | Per pseudo-channel isolation required |
| Command queues | Separate queues per pseudo-channel |

**Recommended**: First-class pseudo-channel with separate command queues.

### Decision 3: Data Rate Extensibility

| Criteria | Evaluation |
|----------|------------|
| JEDEC base | 8 GT/s |
| HBM4E vendors | 12.8 GT/s (Cadence), 16 GT/s (Synopsys/Rambus) |
| Timing scaling | Parameters scale inversely with rate |

**Recommended**: Configurable `data_rate` (8/12.8/16) with precomputed timing tables.

### Decision 4: DFI 5.1 Interface Compliance

| Criteria | Evaluation |
|----------|------------|
| HBM4 requirement | DFI 5.1 mandatory |
| PHY Independent Mode | Required for init/training |
| Protocol handshake | Must model full DFI lifecycle |

**Recommended**: DFI 5.1 compliance from Layer 2.

### Decision 5: Lane Repair Integration

| Criteria | Evaluation |
|----------|------------|
| Research finding | CRITICAL for HBM4E (Cadence explicitly lists) |
| Physical layer | Redundancy mechanism affects yield |
| Reliability | Lane remapping for failed lanes |

**Recommended**: Lane repair as configurable Layer 3 component with repair_map and failed_lane tracking.

## Recommended Implementation Order

1. **Phase A-1**: Layer 2 (HBM Controller) - address decoder, queues, basic scheduler
2. **Phase A-2**: Layer 2 - QoS scheduler, refresh scheduler, DFI encoder
3. **Phase B-1**: Layer 3 (DRAM Model) - bank state machines, channel FSM
4. **Phase B-2**: Layer 3 - lane repair, power model, error tracking
5. **Phase C-1**: Layer 4 (PHY) - DFI 5.1, training FSM
6. **Phase C-2**: Layer 4 - MBIST, loopback, signal integrity
7. **Phase D**: Layer 0/1 - traffic generators, interconnect models

## Key Modeling Assumptions

1. **Channels are independent**: No global synchronous clock; per-channel state.
2. **Pseudo-channels are first-class**: Separate command queues required.
3. **DFI 5.1 is the protocol boundary**: All Layer 2 → Layer 3 commands use DFI encoding.
4. **Lane repair is critical**: Configurable but enabled by default for HBM4E.
5. **40% power efficiency is achievable**: Model tracks power-per-bit reduction.
6. **AI workloads dominate**: Traffic patterns optimized for training/inference.
